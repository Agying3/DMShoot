# DMShoot 版本升级对比：cc84cc0 到当前版本

> 对比基准：`cc84cc0b1ac7831124f918f6021932e86a025f31`  
> 基准提交：`perf: 文件日志INFO级别 + 轮询日志降为DEBUG`  
> 目标版本：本文件所在提交（基于 `6bb326f` 继续升级）  
> 对比日期：2026-08-30

## 1. 结论先说

这次升级不是简单换皮，也不只是把几个动画加到界面上。相比 `cc84cc0`，DMShoot 的核心变化可以概括为：

1. **启动方式从“脚本拼装”收敛为正式桌面程序入口**：正式运行只走 Python，默认无控制台启动，首屏不再被浏览器准备工作阻塞。
2. **扫码登录从“拿到 Cookie 就算成功”升级为完整认证状态机**：扫码前清旧凭据，扫码后原子保存，真实连接后才亮绿灯。
3. **入站消息从多处各自写库升级为单一可靠链路**：落库、去重、会话摘要和未读数在一个事务中完成，成功后才通知 GUI 和 AI。
4. **抖音 WebSocket 从固定轮询升级为事件驱动**：消息到达立即唤醒，每批最多处理 100 条，停止和重连也更可控。
5. **桌面交互从“能点”升级为“有状态、有反馈、不打断”**：非模态设置、五态连接灯、Toast、新消息按钮、增量消息渲染全部落地。
6. **性能优化开始以真实窗口数据做取舍**：经 A/B 实测主动撤销拖慢界面的整页和气泡动画，保留真正有价值的反馈。

一句话总结：**`cc84cc0` 主要解决日志噪声，当前版本已经开始同时解决可靠性、实时性、并发一致性和桌面体验。**

## 3. 总览对比

| 维度 | `cc84cc0` | 当前版本 | 实际价值 |
|---|---|---|---|
| 正式启动 | Python 前台启动，并尝试拉起 Go 服务 | Python 单路径，默认 `pythonw` 无控制台启动 | 更像桌面软件，部署和排障路径更简单 |
| 图形渲染 | 强制软件 OpenGL | Qt 默认选择硬件渲染，环境变量可回退 | 正常显卡环境下减少 CPU 绘制压力 |
| Playwright 准备 | Qt 主线程延迟执行，仍可能阻塞 | 后台守护线程准备 Chromium | 首屏和点击不被安装/检查拖住 |
| 扫码前状态 | 旧 Cookie 和附属认证字段可能残留 | 先停旧监听，再清空平台完整认证字段 | 解决“扫了新码却仍使用旧登录态” |
| Cookie 保存 | 多字段可能分散更新 | 同一批认证字段原子保存 | 避免半新半旧的认证组合 |
| 配置并发 | 旧 `AppConfig` 可能覆盖新 Cookie | 启动前从 DB 原地刷新，设置页字段级保存 | 解决并发窗口造成的配置回滚 |
| 在线绿灯 | 保存 Cookie 后可能提前显示在线 | 真实 WS/适配器连接成功后才为绿色 | 用户看到的状态与真实连接一致 |
| 入站消息 | 各平台和 GUI 存在不同保存路径 | 适配器统一先落库，再发布事件 | 避免重复写库、重复 UI 和重复 AI |
| 消息去重 | 同文消息存在误删或重复风险 | 服务端 `message_key` + 精确时间兜底 | 既挡重复推送，又保留真实重复内容 |
| SQLite 更新 | 消息、会话、未读可能分步执行 | 单事务原子完成 | 崩溃或并发下更难出现半更新 |
| 抖音收消息 | 固定 500ms 轮询 | 事件唤醒 + 每批 100 条 | 消除额外轮询等待，洪峰吞吐更稳 |
| WS 重连 | 停止、异常退出和状态清理不完整 | 可中断等待、指数退避、退出清状态 | 少假在线，关闭和重登更干净 |
| 设置窗口 | 模态阻塞，页面一次性创建 | 非模态，模块预载，重页面懒创建 | 主窗口可继续操作，首次成本更合理 |
| 聊天渲染 | 长会话控件持续累积，容易抢滚动 | 常驻上限、分批加载、阅读缓冲 | 长会话内存和布局成本更可控 |
| 新消息体验 | 查看历史时可能被拉到底部 | 保持阅读位置并显示“X条新消息” | 不打断阅读，用户决定何时回到底部 |
| 操作反馈 | 成功/失败反馈零散或依赖弹窗 | Toast、导航指示条、五态状态灯 | 操作有闭环，同时不阻塞工作流 |
| 性能策略 | 功能实现优先 | 真实 GUI A/B 后取舍动画 | 避免“看起来高级、实际更卡” |

## 4. 启动架构：正式放弃 Go 双轨制

### 4.1 旧版问题

旧 `run.bat` 会先尝试启动 `dmshoot-go/msg-service.exe`，然后再以前台 Python 运行 GUI。这会带来三个问题：

- 同一业务可能存在 Python/Go 两条路径，数据所有权和故障位置难判断。
- 控制台窗口、启动文字和暂停行为让程序更像脚本。
- Go 服务是否存在会改变运行方式，开发环境与用户环境不完全一致。

### 4.2 当前方案

- 正式入口统一为 Python + SQLite，Go 源码可保留研究，但不再参与正式启动。
- `run.bat` 默认通过虚拟环境中的 `pythonw.exe` 启动，无额外控制台窗口。
- 调试时仍可执行 `run.bat --console`，保留完整输出和退出码。
- Playwright Chromium 检查/准备放进后台守护线程，不占 Qt 主线程。
- 不再强制 `Qt.AA_UseSoftwareOpenGL`；只有设置 `DMSHOOT_SOFTWARE_RENDER=1` 时才软件渲染回退。

这次收敛的核心收益不只是“少开一个进程”，而是**配置、消息和数据库职责只剩一个权威实现**，后续维护成本明显下降。

## 5. 登录可靠性：彻底处理旧 Cookie 污染

### 5.1 修复的真实故障链

旧流程可能发生：

1. 本地保留已经过期的 Cookie 或附属票据。
2. 用户重新扫码，浏览器拿到了新登录信息。
3. 旧 `AppConfig`、旧监听器或未清理字段继续参与连接。
4. 设置窗口随后全量保存旧配置，又把新 Cookie 覆盖回去。
5. UI 因“Cookie 已保存”提前亮绿灯，但实际监听没有成功。

最终表现就是用户看到扫码成功，却没有真正登录或收不到消息。

### 5.2 当前完整处理

扫码前先停止对应平台旧监听，并清理整组认证字段：

| 平台 | 清理/更新字段 |
|---|---|
| 抖音 | Cookie、`web_protect`、`keys` |
| B站 | `SESSDATA`、`bili_jct`、`buvid3`、`buvid4`、用户 ID、刷新值 |
| 小红书 | 平台 Cookie |
| 快手 | 平台 Cookie JSON |

随后通过 `update_config_fields()` 在同一事务内保存整组新字段。`AuthController` 和 `AdapterManager` 每次连接前都从 SQLite 原地刷新共享 `AppConfig`，设置页只提交自己负责的字段，认证字段不会再被旧窗口覆盖。

状态语义也被纠正：

- **灰色/准备状态**：只表示 Cookie 已保存或当前未连接。
- **黄色连接中**：正在启动或等待握手。
- **橙色重连中**：连接中断，正在自动恢复。
- **绿色在线**：真实监听连接已经建立。
- **红色错误**：认证失效或不可恢复错误。

所以当前的绿灯是连接事实，不再是保存动作的装饰反馈。

## 6. 消息链路：从“尽量保存”到事务级可靠

### 6.1 单一入站路径

当前各平台收到消息后统一经过 `BaseAdapter._on_message()`：

1. 适配器线程解析平台消息。
2. 调用数据库统一持久化入口。
3. SQLite 在一个事务中插入消息、更新会话摘要、增加未读数。
4. 只有首次插入成功才发布到消息总线。
5. GUI 和 AI 收到的必然是已落库且未重复的消息。

这解决了旧版可能出现的三类重复副作用：重复数据库记录、重复刷新气泡、重复触发 AI 回复。GUI 主线程也不再负责入站 SQLite 写入，减少消息洪峰时的卡顿来源。

### 6.2 两级精确去重

所有核心消息模型、API 和平台适配器新增 `message_key`：

- 有服务端消息 ID 时，按平台和服务端 ID 构造唯一键。
- B站等场景会把会话 ID 纳入键，避免不同会话序号碰撞。
- 无服务端 ID 时，按会话、发送者、内容、方向和精确时间戳兜底。
- SQLite 自动迁移旧数据库并建立条件唯一索引。

这意味着：

- 平台重推同一条消息：只处理一次。
- 同一个人真的连续发送两条相同文字：只要服务端 ID 或时间不同，两条都保留。
- 不同会话出现相同文本：不会互相误删。

### 6.3 数据一致性补强

- 占位昵称不会再覆盖已经补全的真实昵称。
- 清理消息缓存时保留联系人会话，避免联系人列表一起消失。
- B站、小红书与抖音统一使用同一持久化契约。
- API 模型同步携带 `message_key`，避免边界层丢失唯一标识。

## 7. 抖音 WebSocket：固定轮询改为事件驱动

### 7.1 旧版成本

固定每 500ms 检查一次队列，会人为增加 0-500ms 等待。均匀分布时平均约 250ms，P95 约 475ms；这不是网络慢，而是程序自己在等下一次轮询。

### 7.2 当前机制

- WebSocket 收到消息后立即触发线程安全唤醒。
- asyncio 消费者被唤醒后马上读取队列。
- 单批最多处理 100 条；队列仍有数据时立即继续，不额外睡眠。
- 无消息时等待事件，同时保留低频超时作为兜底。
- 真实 `_on_open` 回调后才设置 `connected=True`。
- wrapper 异常退出、错误或关闭后都会清除连接状态。
- 停止事件可立即打断重连等待，关闭程序或重新扫码不用干等。
- 连续握手失败采用指数退避，成功连接后恢复初始间隔。
- 联系人资料补全和刷新增加节流，避免消息高峰附带大量资料请求。

结果是日常消息更快出现，消息高峰也不会因为每批固定休眠而越积越多。

## 8. 设置页和配置所有权

### 8.1 非模态和懒加载

- 设置窗口由 `exec_()` 改为 `show()`，打开后主窗口仍可操作。
- 设置模块在后台预载，降低第一次点击时的导入抖动。
- 主题页和性能页首次进入时才创建，避免为不使用的重页面提前付费。
- 页面精简为回复、主题、数据、性能和调试五类。

### 8.2 字段级保存

设置页不再把整个旧 `AppConfig` 覆盖回 SQLite，而是仅保存界面实际拥有的字段。扫码线程写入的 Cookie、票据和刷新值不属于设置页事务，因此不会再被并发覆盖。

抖音、B站和快手限流值保存后会实时同步到内存限流器，不需要重启。API 也补齐快手限流配置，数据库继续作为唯一配置源。

### 8.3 调试能力

新增分类日志控制入口，可分别观察：

- AI 思考过程
- 消息同步
- Go 服务遗留调试分类
- API 耗时
- PerfChart

正式运行可以保持安静，定位问题时再只打开需要的类别。

## 9. GUI 感知流畅度

### 9.1 聊天视图增量化

当前聊天窗口采用明确的渲染预算：

| 项目 | 当前值 |
|---|---:|
| 初始加载 | 12 条 |
| 每次补载历史 | 4 条 |
| 正常常驻气泡 | 最多 50 条 |
| 阅读历史额外缓冲 | 20 条 |

长会话不再让 QWidget 气泡无限常驻，布局计算和内存占用随消息总量增长的问题得到控制。用户停留在底部时保持自动跟随；用户向上阅读时保持当前位置，并显示“X条新消息”按钮，点击后再回到底部。

### 9.2 有用的反馈留下，昂贵的动画撤掉

已落地：

- 侧边栏 150ms 移动指示条。
- 平台五态状态灯及悬停详情。
- 设置保存、登录信息保存、登录失效、发送失败、缓存清理等非模态 Toast。
- Toast 与新消息按钮经过真实窗口检查，不互相遮挡。

经 A/B 后撤销：

- 整页透明切换动画。
- 每条聊天气泡淡入动画。

原因很直接：它们显著增加透明合成和事件循环压力，视觉收益小于性能损失。当前版本选择“状态反馈清楚”而不是“动画数量多”。

## 11. 修复的隐藏问题

除了用户直接可见的登录和流畅度问题，本轮还处理了几处容易长期潜伏的错误：

1. **限流统计死锁**：修复同一流程重复获取同一把 Lock 的问题。
2. **WS 假在线**：wrapper 异常退出但未触发 close 时，强制清除 connected。
3. **无法及时停止重连**：普通 sleep 改为可被停止事件打断的等待。
4. **旧配置覆盖新认证**：设置页与扫码线程重新划分字段所有权。
5. **同文消息误去重**：优先使用服务端 ID，不再只依赖文本特征。
6. **重复消息触发 AI**：数据库确认首次插入后才发布消息事件。
7. **测试假绿**：自运行测试脚本内部断言失败时会返回非零退出码，不再最后仍显示通过。

## 13. 仍然存在的边界

当前版本明显进步，但不是“性能问题全部消失”：

1. **冷启动仍受 Python/PySide6 导入成本影响**。后台准备 Playwright 已避免额外阻塞，但 Python 桌面程序本身仍有基础启动开销。
2. **聊天区仍是 QWidget 气泡，不是真正虚拟列表**。50+20 的窗口化策略足以覆盖日常使用，极端瞬时洪峰仍有继续优化空间。
3. **首次打开性能页仍是重操作**。现在通过懒创建把成本推迟到真正使用时，后续可增加紧凑加载反馈和固定采样频率。
4. **完整 682 项 pytest 本轮未在当前环境重跑**。原因是当前虚拟环境和系统 Python 缺少 pytest；本轮完成的是 237 项专项回归及真实 GUI 验证。
5. **Go 源码仍在仓库中**。它不参与正式启动，后续可在确认无历史工具依赖后单独归档或删除。

## 14. 对独立开发的实际意义

这次升级最“值钱”的部分不是某个按钮或某个数字，而是把几个高风险边界收紧了：

- 登录状态由数据库、扫码线程、设置窗口各自理解，变成明确的认证字段所有权。
- 消息由平台、GUI、AI 各自处理，变成“先可靠落库，再向上发布”的单向链路。
- 实时性由定时检查队列，变成消息到达主动唤醒。
- 桌面体验由增加动画，变成用真实数据筛选反馈方式。
- 正式运行由 Python + Go 双轨，变成一个可理解、可测试、可维护的 Python 路径。
